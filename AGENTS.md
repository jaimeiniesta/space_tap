# AGENTS.md

Instructions for AI coding agents working on this repository.

## What this is

SpaceTAP is an Elixir client for the IVOA Table Access Protocol (TAP), the HTTP protocol astronomical archives use to expose tabular data. Queries are written in ADQL and results come back as VOTable (or CSV and other formats).

This is not the Test Anything Protocol. Keep that in mind when searching for references or naming things.

Specifications:

- TAP 1.1: https://www.ivoa.net/documents/TAP/20190927/REC-TAP-1.1.html
- Related IVOA standards: DALI, UWS (async jobs), VOTable, ADQL.

We target TAP 1.1 and stay compatible with TAP 1.0 services. When a behaviour comes from the spec, cite the section in code comments or docs.

Name things with the terms defined in `GLOSSARY.md`. Decisions with their reasoning and rejected options are recorded as ADRs in `docs/adr/`.

## Scope

Stick to the scope of the version being worked on. If an idea belongs to a later version, suggest it instead of implementing it.

## Working on this project

- Work in small steps. For anything larger than a small change, propose a plan before writing code.
- Explain the reasoning behind design decisions and point to the relevant part of the spec.
- Ask before adding dependencies, committing, pushing, tagging or publishing to Hex.
- Code, docs, README, CHANGELOG and commit messages are in English.

## Design decisions already made

- Public entry points: `SpaceTAP.query(service_url, adql, opts)` for a sync query and `SpaceTAP.async_query(service_url, adql, opts)` for an async one, both returning `{:ok, %SpaceTAP.Result{columns: [...], rows: [...]}}` or `{:error, %SpaceTAP.Error{}}`. A struct rather than a list of maps, so column order is kept and conversion to dataframes is easy.
- Errors: one exception, `%SpaceTAP.Error{type, message, status}`, with types `:service_error`, `:http_error`, `:transport_error`, `:decode_error`, and `:timeout` for a wait for an async job that runs out. The response body decides the type before the HTTP status (`docs/adr/0001-one-error-struct-with-a-type.md`).
- `service_url` is the base URL of the service, the TAP 1.1 §2.4 access URL. Trim trailing `/`s and append `/sync`, or `/async` for a job, treating every `service_url` as a base URL, even one that already ends in `/sync`.
- Sync queries, and the jobs of async ones, POST `REQUEST=doQuery`, `LANG=ADQL` and `FORMAT=csv`. `REQUEST` is required by TAP 1.0 (§2.3.1), and a TAP 1.1 service must ignore it (§2.7). `FORMAT` goes alone and in lowercase: TAP 1.1 services must accept it as equivalent to `RESPONSEFORMAT`, sending both is undefined (§2.7.3), and parameter values are case sensitive (DALI §3.1).
- VOTable results come with `format: :votable`, which sends `FORMAT=votable`; CSV stays the default. The format decides the value types, so a VOTable sent for a CSV request is a `:decode_error` that points to `format: :votable` (`docs/adr/0006-the-format-option-decides-the-value-types.md`). SpaceTAP reads TABLEDATA, BINARY and BINARY2, told apart by the child of `DATA`, and FITS is a `:decode_error` (`docs/adr/0005-read-the-serialization-the-service-sends.md`), and so is data not inside the document in base64: a `STREAM` with an `href` or another `encoding`, or a `TD` with an `encoding` (VOTable 1.5 §5.6). A `FIELD` SpaceTAP can't read, with an unknown or unsupported datatype or an invalid `arraysize` or `VALUES null`, is a `:decode_error` even when no cell uses it, and so is a `FIELD` after the `DATA`, which comes last in a `TABLE` (VOTable 1.5 §3.8), since TABLEDATA rows become values as they arrive. Cell values follow `docs/adr/0007-how-votable-values-map-to-elixir.md`. `SpaceTAP.Result` gains `fields` (`[%SpaceTAP.Field{}]`) and `overflow` (a boolean), both `nil` for CSV.
- Options: `:maxrec` maps to `MAXREC` and takes a non-negative integer; `0` is sent and returns the columns with no rows (DALI 1.1 §3.4.4). `:req_options` is merged into `Req.new/1`: tests inject `plug: {Req.Test, SpaceTAP}`, or `{Req.Test, SpaceTAP.Job}` for async, through it, and users raise Req's default 15 s `receive_timeout` with it (long queries belong to `async_query/3`). SpaceTAP's own Req options win the merge, including `decode_body: false`, `http_errors: :return` and `into: nil`, which keep the `{:ok, _}`/`{:error, _}` contract; `retry: false` is a default `:req_options` overrides, so each request is sent once unless the caller sets `:retry` (`docs/adr/0016-each-request-is-sent-once.md`); any other option, such as `:headers`, goes to Req as given. Unknown options raise `ArgumentError` via `Keyword.validate!/2`, and so does a `:req_options` that isn't a keyword list. No application config.
- Most services send error documents as VOTable even when CSV was requested. Only the `INFO name="QUERY_STATUS"` elements directly inside the `RESOURCE type="results"` count, found by name among the other `INFO`s services add (DALI §4.4), and a VOTable without exactly one such resource, or one without a `QUERY_STATUS`, is a `:decode_error`. `ERROR` is a `:service_error` whose message is the element's trimmed content, or a message of SpaceTAP's own when that content is empty, since it is optional (DALI §4.4.2); it wins over a table it follows, which may be cut short. `OVERFLOW`, before or after the `TABLE`, sets `overflow` (§4.4.1). `OK` or `OVERFLOW` without exactly one `TABLE` is a `:decode_error` (TAP 1.1 §3.2). KOA and CADC send plain text with HTTP 400, which is a `:service_error` too; plain text with any other error status is an `:http_error`, because a proxy may have written it (`docs/adr/0004-plain-text-with-400-is-a-service-error.md`).
- Parse XML with Saxy, chosen over `:xmerl_sax_parser` by a benchmark on 100,000 rows of Gaia DR3: xmerl hands the base64 text of a BINARY2 `STREAM` over as a charlist, 16 bytes per character (`docs/adr/0008-read-votable-with-saxy.md`). Saxy skips the DTD and expands none of its entities, so a reference to any entity but the five XML predefines is a `:decode_error` rather than text in a cell. Saxy keeps namespace prefixes on element names, so match the local name.
- CSV: the first row is always the header, whatever the `header=` media-type parameter says (TAP 1.1 §3.2). An empty cell becomes `nil`: no spec defines NULL in CSV, and Gaia sends an empty field. A 2xx `text/plain` response is read as CSV too, because the NASA Exoplanet Archive and KOA label CSV that way; no other type is (`docs/adr/0003-csv-sent-as-plain-text-is-read-as-csv.md`).
- The client is stateless. No GenServer or supervision tree: async UWS jobs live on the TAP service, and waiting for one is polling with backoff in the caller's process.
- Async queries are UWS jobs (TAP 1.1 §2.2). `SpaceTAP.Job` has the steps, `submit/3`, `wait/2`, `result/2`, `get/2` and `delete/2`, and `async_query/3` uses them alone and deletes the job whatever happens (`docs/adr/0010-async-query-starts-waits-for-and-deletes-a-job.md`). Create the job without `PHASE=RUN`, accept only a 303 to it (UWS 1.1 §2.2.3.1), not one to the list of jobs, and send `PHASE=RUN` only to a PENDING job (DALI 1.1 §2.1). Wait with `WAIT=30`, never `-1` (UWS 1.1 §2.2.1.2), the seconds left at most and without `WAIT` under a second, pausing from 1 to 30 seconds, 1.5 times longer each time, when the service answers early with the same phase; `:timeout` is `:infinity` by default. Read the href of the `result` whose id is `result` (UWS 1.1 §2.2.2.3). Delete with DELETE, then POST `ACTION=DELETE` if that fails, without following the 303 (UWS 1.1 §2.2.3.2). A job that stops in a phase other than COMPLETED is a `:service_error` with its error summary.
- Every URL a service lists, the job URL of the 303, the result URL of a job document and the availability URL of the capabilities, is read by one rule, in `SpaceTAP.HTTP.listed/4`: never over `http://` after `https://`, so an `http://` URL on the host of the URL the client gave is read with `https://`, and one on another host is a `:decode_error` and isn't read; credentials, the `authorization` header and Req's `:auth`, stay with the scheme, host and port of the URL the client gave, hosts compared without regard to case (`docs/adr/0015-listed-urls-are-read-by-one-rule.md`). A relative URL is resolved against where the redirects led (RFC 3986 §5.1.3). A `SpaceTAP.Job` keeps the service URL `submit/3` was given in `service_url`, `nil` for a job from `get/2`, so `wait/2`, `result/2` and `delete/2` send the credentials of each call's `:req_options` to the job by the same rule, through `SpaceTAP.HTTP.credentials/3`.
- `SpaceTAP.Result.to_dataframe/1` gives each column the Explorer dtype of its field's datatype at the same width (`float` is `{:f, 32}`) and an array a nested list, every column of a CSV result `:string`, and a repeated column name a number after it, as PyVO names it (`ra2`). It checks for Explorer when called and raises `ArgumentError` without it (`docs/adr/0011-to-dataframe-takes-the-types-of-the-fields.md`).
- `SpaceTAP.tables/2` and `SpaceTAP.columns/3` read `TAP_SCHEMA` (TAP 1.1 §4) with `SELECT *` as a sync query in VOTable, by each column's standard name in lower case, and sort the rows by `table_index` or `column_index` themselves. A list marked as overflow comes back with a `Logger.warning`, since MAST marks every result so (`docs/adr/0013-table-metadata-comes-from-tap-schema.md`).
- `SpaceTAP.availability/2` takes the availability URL from `<service URL>/capabilities` (DALI 1.1 §2.5), reads both documents as XML also when they have no `Content-Type`, as KOA sends them, and returns an availability document whatever its HTTP status. It shares the URL rule of `Job.result/2`, in `SpaceTAP.HTTP`: an `http://` URL on the service's host is read with `https://`, one on another host is a `:decode_error`, and credentials stay with the service's host (`docs/adr/0014-availability-is-found-through-capabilities.md`).
- No Ecto-style query builder. `SpaceTAP.ADQL` returns ADQL text and sends nothing: `literal/1` for values and `cone/5`, which writes `CONTAINS(POINT('ICRS', ...), CIRCLE('ICRS', ...)) = 1` (`docs/adr/0012-adql-helpers-write-plain-text.md`).

Agreed dependencies: `req`, `nimble_csv` and `saxy`, plus `credo`, `dialyxir` and `ex_doc` (`only: [:dev, :test], runtime: false`) for development, `plug` (`only: :test`), which `Req.Test` needs, and `explorer` (`~> 0.13`, `optional: true`) for `to_dataframe/1`. The livebooks also install `kino`, `kino_explorer` and `vega_lite`. Discuss any other dependency before adding it.

## Code and tests

- Use `mix format`. Public functions get `@spec`, and those of documented modules get `@doc`; internal modules (`@moduledoc false`) explain themselves in comments. Public types get `@typedoc`. Add doctests when they don't need the network.
- Unit tests use `Req.Test` stubs and never touch the network.
- Integration tests hit real services, are tagged `@tag :integration` and are excluded by default in `test/test_helper.exs`. Run them with `mix test --include integration`. Their target is GAVO (`https://dc.g-vo.org/tap`), on `gaia.dr3lite`, its copy of Gaia DR3, because it answered every check in the weeks before 0.2.0 (`docs/adr/0009-gavo-is-the-service-releases-are-tested-against.md`). They run queries sync and as async jobs, and call `tables/2`, `columns/3` and `availability/2`. Keep those queries small (`TOP 5` or similar) to be polite to the service, and give an async query a `:timeout`, which deletes its job, shorter than the test's own, since a job may wait in a queue for minutes.
- Services tests send the queries of each service's fixtures to the other services in the README's Compatibility table and check that they still answer the same way. They are tagged `:services`, excluded by default and run with `mix test.services`. A failure there is a reason to look into that service, not a release blocker, so `mix test.release` leaves them out. They run the query of each result fixture as an async job too, which the NASA Exoplanet Archive, KOA and IRSA keep after a delete. They ask every service for its availability, and the services with a `metadata` entry in `test/support/services.ex` for the table of their `TAP_SCHEMA` fixtures and one of its columns, or for the error its `tables_error` gives instead, as at Gaia. When a service changes how it answers, capture its fixture again and update both tests; a SpaceTAP bug it reveals gets its own issue.
- Parity tests run the same queries through SpaceTAP and through PyVO (an Astropy-affiliated Python client for IVOA services, used as reference implementation) against live services, and compare the results. Those for GAVO are tagged `@tag :pyvo`, excluded by default, and run with `mix test --only pyvo` and `mix test.release`; those for every service in the Compatibility table, Gaia and the NASA Exoplanet Archive included, are tagged `:services` and run with `mix test.services`, so an outage at one of them doesn't hold a release. Both read their services and queries from `test/support`, shared with the services tests. They call a PEP 723 script through `uv run`, which pins PyVO and astropy and prints JSON; without `uv` they skip locally and fail when `CI` is set. They compare the columns, overflow and the values of every row, sorted, of the VOTable both clients read, and check that SpaceTAP's CSV has the same columns and as many rows. The same queries run as async jobs in both clients, with PyVO's steps, a wait that polls the phase rather than PyVO's `WAIT=-1`, which GAVO cuts after about 120 seconds, and a delete that, like SpaceTAP's, doesn't fail the test; NED is left out, since PyVO can't read its job documents and would leave its job there. They also compare a service's tables by name, the columns of one table by name, unit and UCD, and its availability: PyVO reads `/tables` where SpaceTAP reads `TAP_SCHEMA`, so the two sources are compared too.
- Parity tests on the fixtures need no network: both clients read every VOTable in `test/fixtures/*/*.xml`, the rows are compared in the order of the file, and the data frame of each result has the column names and dtypes of PyVO's `to_table()`. A file both refuse, such as an error document, passes. `capabilities.xml` and `availability.xml` are read as VOSI, by the availability URL of the first and the fields of the second. The job documents in `test/fixtures/*/jobs/` are compared the same way, by their phase, error summary and result; PyVO can't read NED's, whose times carry a UTC offset, and the test checks that it still can't. They are tagged `:pyvo_fixtures`, excluded by default, and run with `mix test --only pyvo_fixtures`, `mix test.release` and in CI.
- CI runs the lint checks, the unit tests and the parity tests on the fixtures. Run integration and the other parity tests locally before a release.
- Fix Dialyzer warnings in the code. `.dialyzer_ignore.exs` holds only ExUnit idioms in `test/support`.
- Before saying a change is done, run `mix format --check-formatted`, `mix compile --warnings-as-errors`, `mix credo --strict`, `mix dialyzer`, `mix test` and `mix docs --warnings-as-errors`, and report the results.
- After changing dependencies, run `mix hex.audit` to check that none has been retired.
- Keep `CHANGELOG.md` up to date following Keep a Changelog.
